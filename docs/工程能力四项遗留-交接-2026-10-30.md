## 1. 累计花费并发丢增量（建议先做）

**问题**：`SPEND` 是 `AtomicU64` 存 f64 的 bits，累加走「load → 加 → store」的读改写。

`src/usage/mod.rs:222-226`：
```rust
if let Some(c) = rec.cost_usd {
    let cur = f64::from_bits(SPEND.load(Ordering::Relaxed));
    SPEND.store((cur + c).to_bits(), Ordering::Relaxed);
}
```
两个请求同时结束 → 都读到同一个旧值 → 各自加完写回 → 只记了一次增量。多会话并发 + 摘要/标题辅助调用同时记账是常态，不是边界情况。

**为什么重要**：`cap_block()`（`src/usage/mod.rs:298` 附近）读的就是 `SPEND`，那是 README 里的「红线一：全局花费上限」硬闸。少记 = 超支放行。

**根因**：`AtomicU64` 存 f64 bits 没有可用的 CAS 累加（f64 不能直接 `fetch_add`）。三条路可选：

- **A（推荐）**：把 `SPEND` 换成 `Mutex<f64>`（或 `RwLock<f64>`）。读点只有 `spend_total()`（`:279` 附近）和 `recompute` 的写点，改动小、语义直白。
- **B**：CAS 循环（`compare_exchange_weak`），无锁但要处理 ABA 和 f64 比较，容易写错。
- **C**：把累加挪进 ledger 的文件锁区间里一起做——顺带解决 `recompute()` 的窗口问题（见下）。

**同时要处理的竞争**：`recompute()`（`:236-262`）是「读全表 → 原子写新文件 → `SPEND.store(total)` → `reopen()`」。在这个窗口里 `record()` 追加的行会随旧文件被替换而**永久丢失**（`reopen` 只换句柄，不补记录）。价格页保存会自动触发 recompute（`src/server/usage.rs:120` 附近），所以这是用户可触发的。

**验收标准**：
- 新增单测：N 个线程并发 `record()` 各记已知金额，最后 `spend_total()` 必须精确等于预期总和（别用浮点容差糊过去，用能精确表示的值，如 0.01 的整数倍）。
- 新增单测：recompute 与 record 并发时不丢记录（可用一个可控的 barrier 或直接断言「recompute 后台账行数 ≥ recompute 前的行数 + 期间 record 的次数」）。
- `cargo test` 全绿；clippy 零告警。

**注意**：`record()` 在未初始化时是**静默 return**（测试里必须先拿到 `ledger()` 单例再记，否则断言全飘——ROADMAP 坑 19 记过）。

## 2. 浏览器 / MCP 全局锁跨网络 await 持有

**浏览器侧**：`src/browser/mod.rs:354`
```rust
static SESSION: Mutex<Option<Arc<BrowserSession>>> = Mutex::const_new(None);
```
`panel_state()`（`src/browser/panel.rs:17`）拿着这把锁做了三件很慢的事：
- `browser_alive(port)` —— HTTP 探活，3s 超时（`:23`）
- `reap_dead_tabs(&mut guard)` —— 逐 tab 关页（`:32`）
- `s.tab_briefs()` —— 每 tab 两次 CDP evaluate，单次 10s 预算（`:36`）

而前端每 2s 轮询 `/api/browser/state`（`web/src/App.svelte` 的 `webStartAgentWatch`）。页面挂起（弹窗、JS 死循环）时，面板轮询会长时间占住锁，agent 的 browser 工具（走 `current_session()`）只能排在后面——表现就是「agent 卡在浏览器工具上」。

**MCP 侧**：`src/mcp/mod.rs:116`
```rust
static MANAGER: OnceLock<Mutex<HashMap<String, ServerState>>> = OnceLock::new();
```
`tools/call` 在 `spawn_blocking` 里**持锁走完整个 rpc**（`:840` 附近），预算 120s。而 `risk_for()`（`:722`，每个工具每次审批判定都调）和 `tool_definitions()`（`:775`）用的是同一把锁，且都在 async worker 上同步 `lock()`。一个卡住的 MCP server 会让**所有**后续工具的风险判定阻塞在 tokio worker 线程上——不是简单串行化，是阻塞异步执行器。

**修法方向**（浏览器侧）：
- `panel_state` 的锁内只做「快照」：取 `Arc<BrowserSession>` 克隆 + tab 列表克隆，立刻放锁，然后在不持锁的情况下做 `browser_alive` / `tab_briefs`。
- `reap_dead_tabs` 需要 `&mut guard`，要改成「先算哪些该摘（只读 + 少量 await），再单独拿锁做摘除」。
- 死的会话回收（`kill_child`）可以在锁外做。

**修法方向**（MCP 侧）：
- 每 server 一把锁（`HashMap<String, Arc<Mutex<ServerState>>>`），避免跨 server 互相拖累。
- `risk_for` / `tool_definitions` 改成读一份轻量快照（`enabled` / `online` / `tools` 的克隆），不再和 `rpc_round` 抢同一把锁。

**验收标准**：
- 新增回归测试：模拟一个「慢 server」/「慢浏览器」，断言在它卡住期间 `risk_for` / `tool_definitions`（或 `panel_state` 的快照读）仍能在毫秒级返回。
- 手动真机：开一个会卡的页面（`while(true)`），确认 agent 此时调 browser 工具能得到明确错误而不是无限等待；面板轮询不阻塞主线程。
- 全部现有测试绿。

**风险**：这把锁串起了会话生命周期（ensure_session / current_session / panel_state / 工具调用），改锁粒度容易漏掉「会话刚刚被杀、快照已过期」的竞态。建议**分两个提交**：先改面板路径（`panel_state` 是只读的，最安全），再改工具路径。

## 3. 对话轮 panic 无人接

**问题**：`src/server/chat/mod.rs:373` 与 `:389` 两处 `tokio::spawn(async move { ... })`，`JoinHandle` 被丢弃。全仓没有 `catch_unwind`，也没有处理 `JoinError`（`rg JoinError` 只在 `src/server/system.rs:189` 的沙箱自检）。

**后果链**：任何 panic → spawn 任务静默 unwind → `tx`（SSE sender）被 drop → 流直接结束、`done` 事件从没发出 → 前端 `finally` 把空回答气泡删掉、清掉流登记。用户看到的就是「消息发出去，什么都没了」：没有错误气泡、没有日志（logger 也没挂 panic hook）。

**修法**：
1. spawn 内包一层 `AssertUnwindSafe(fut).catch_unwind()`，捕到就把 panic 信息转成一条 `error` 事件推给前端 + 落 JSONL。
2. 或者用 `JoinSet` / 保留 `JoinHandle`，在 `JoinError::is_panic()` 时补发 `done` + `error`。
3. `std::panic::set_hook` 里落一条 JSONL（`EventType::Error` + `kind: "panic"` + backtrace 摘要），这样即使不在 chat 路径上的 panic 也能留痕。

**为什么排第三不是第一**：这项是「放大器」而不是 bug 本身——它不制造问题，只是让已有的问题从「看不见」变成「看得见」。做完之后，第 1、2、4 项出问题时更容易定位。

**验收标准**：
- 新增测试：构造一个必然 panic 的内核/工具（可在测试里注入），断言前端收到 `error` 事件、JSONL 里有 `panic` 记录，且**不**留下「会话永远 running」的僵尸状态（`/api/cancel?session=` 的返回必须是 idle）。
- 手动真机：临时插一个 `panic!()` 到某个工具执行路径，确认用户看到的是错误气泡而不是空白。
